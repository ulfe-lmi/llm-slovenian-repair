### D1-3: Fix mechanism for the 51 B v2 residual

Dilemma: the v2 hidden acceptance exposed 51 B (3 of 2,000 documents,
all T10-randomized): (1) 35 B in one document - an adjacent
structured-html closing tag opens a CommonMark HTML block that absorbs
the code fence plus part of the code body until an internal blank line;
the remaining code lines parse as paragraph and are exposed; (2) 16 B in
two documents (same component) - a structured-keyvalue component
embedding Markdown list items with quoted emphasis parses as
list+strong/emphasis, exposing quote characters plus one word. The
008-g report names two fix levels: a builder-side T10 composition
adjacency guard, or a label-oracle refinement. A further residual
recognizer is excluded by the 008-g verdict.

Governing authority: the 008-g named scope (builder/label-oracle level,
not residual); the 2026-09-17 human architecture decision (parser owns
Markdown structure; the residual layer stays bounded to the named
machine-significant categories; no ever-growing regex grammar); the
2026-09-17 human hidden-set decision (new independent hidden set after
fixes).

Evidence: 008-g 51 B attribution with mechanism (committed, data-free);
the identical 51 B under the frozen 008-c implementation (pre-existing
dialect-interaction gap, not a fix regression); the dialect's HTML
block-start rule (a closing tag line can open an HTML block that runs to
the next blank line) is the root cause of the 35 B shape; the dialect's
list+emphasis parsing is the root cause of the 16 B shape. Both shapes
are composition-level facts: the builder composes the adjacency; no
pipeline component can protect code lines once the dialect stops seeing
a code block (there is no residual class for bare code text, and adding
one is excluded).

Alternatives compared: (a) composition-contract normalization - the
builder (i) inserts a blank-line separator so a fenced/indented code
component is never composed immediately after an HTML closing-tag line
(R1; the document still contains HTML then code, but the dialect parses
the fence as a genuine code block), and (ii) admits no structured-keyvalue
component containing list-item-style lines with quoted emphasis into the
v3 pool (R2; the same shape in real LLM output is documented as a
policy-exposed dialect-ambiguity class, not pretendable away). The
ambiguous no-separator variants are retained in a VISIBLE dev-edge batch
labeled policy-exposed, so the behavior on the exact v2 shape is
deterministic and regression-tested rather than hidden from evaluation.
(b) label-oracle-only refinement - keep the ambiguous compositions in
the acceptance corpus and label those regions policy-exposed via a
dialect-semantics rule set in the oracle. Rejected as the primary
mechanism because encoding the dialect's block semantics as a parallel
rule set in the label oracle creates drift risk between the oracle's
rules and the actual dialect behavior on the fresh pool (a mislabeled
region distorts the safety metric in an invisible way), while
normalization removes the ambiguous bytes from the acceptance contract
entirely and keeps the label oracle (the implementation residual
function) untouched. (c) further residual recognizer - excluded by the
008-g verdict.

Choice: (a) - R1 separator rule + R2 component admission + declarative
policy v4 classes documenting both shapes (and the v1 sub-shapes, see
Scope item 3) as policy-exposed dialect-ambiguity with the v1/v2
measured evidence, plus the visible dev-edge batch. The label oracle is
NOT extended with dialect-semantics rules.

Mitigation and tests: R1 is a one-blank-line insertion recorded in the
composition provenance (the inserted bytes are labeled neutral
delimiter); R2 is a component-admission rule recorded in the generation
